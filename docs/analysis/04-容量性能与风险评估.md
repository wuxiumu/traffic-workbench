# 04 · 容量、性能与风险评估

> 状态：已确认 ｜ 前提：4 核 8GiB 单机，Docker 双容器（app + redis）

## 1. 内存预算

| 组件 | 估算 | 说明 |
|---|---|---|
| Next.js standalone | 150–250 MB | v1 实测 103MB，加 ioredis/cron 上浮 |
| Redis 空载 | ~5 MB | — |
| Redis 数据（7 天窗口） | 见下表 | 按键结构逐项估 |
| 系统 + Nginx + 余量 | ~1.5 GB | — |

**Redis 窗口内存估算**（单站点，日 PV = P，7 天窗口）：

| 结构 | 每事件开销 | 日 P=1万 | 日 P=10万 |
|---|---|---|---|
| events LIST（JSON ~150B 封顶 10 万条） | ~160 B | 1.6 MB/日 | 16 MB/日 |
| stats HASH | 摊薄≈0 | ~0 | ~0 |
| vis/ips SET（去重后 V 个，~40B/个） | 按 UV≈P/3 | 0.13 MB/日 | 1.3 MB/日 |
| pages/refs ZSET（~200 页/来源，member 均摊） | 摊薄≈0 | ~0.1 MB | ~0.2 MB |
| **7 天合计** | — | **~13 MB** | **~125 MB** |

结论：日 10 万 PV 规模下 Redis 用量 ~125MB，`maxmemory 512mb` + `allkeys-lru` 兜底；8G 内存整体充裕。

## 2. 性能预估

- **采集热路径**：1 次站点缓存 GET（300s 内命中）+ 1 个 pipeline（10+ 命令）≈ 亚毫秒级；Redis 单线程 10 万 QPS 级容量，4c8g 下瓶颈在 Next.js 路由而非 Redis
- **归档任务**：LRANGE 批量 + SQLite 事务批量 INSERT，10 万事件约 2–5 秒；凌晨 3 点执行无业务冲突
- **大盘查询**：窗口内 7×HGETALL + 少量 ZREVRANGE（pipeline 一次往返）；历史段走索引化日聚合表

## 3. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Redis 数据丢失（宕机/重启） | 丢窗口内实时数据，历史不受影响 | AOF（appendonly yes）+ docker 卷；启动补跑归档 |
| flush 与写入并发 | 今日键跳过，理论无冲突；跨天瞬间事件 | 归档只处理 date < today；补跑幂等 |
| RETENTION_DAYS 配置过大 | 窗口键堆积、内存涨 | EVENTS_CAP_PER_DAY 封顶 + maxmemory LRU + 文档给出内存公式 |
| 归档积压（cron 长期未跑） | events 键在 TTL 内未归档即过期 → 丢该日明细 | TTL 加 2 天缓冲；启动补跑；health 暴露最老未归档键可观测（后续） |
| SQLite 归档无限增长 | 磁盘慢性消耗 | ARCHIVE_DAYS=90 自动 DELETE；备份脚本轮换 |
| 时区跨天歧义 | 日期归属错位 | 统一 APP_TZ（默认 Asia/Shanghai）服务端判定 date |

## 4. 可观测性

- `/api/health`：`redis: ok|error`（PING）+ SQLite 探活 + 进程/系统/磁盘指标
- flush 日志：归档条数、站点-天数、耗时（stdout，docker logs 可查）
- 手动触发端点返回 FlushResult（days/archived/cleaned/durationMs），便于巡检
