# 02 · 原架构现状分析（v1 纯 SQLite）

> 状态：已确认 ｜ 关联：`docs/analysis/03-Redis-SQLite混合存储架构分析.md`

## 1. v1 数据流

```
/api/collect → recordPageView() → SQLite 单事务：
  INSERT events
  INSERT OR IGNORE visitor_daily / ip_daily（去重表）
  UPSERT daily_stats / page_daily / referrer_daily（增量聚合）
工作台读 → 全部查日聚合表
```

## 2. 优点

- 零外部依赖，单文件备份，事务保证一致
- 写入即聚合，读路径永远是小表查询
- 4c8g 上实测常驻 ~103MB，支撑日百万 PV 无压力

## 3. 与 v2 需求的差距

| 差距 | 说明 |
|---|---|
| 热路径绑死 SQLite | 每次上报都是磁盘事务；高并发写时 WAL checkpoint 可能抖动 |
| 无实时能力 | 「最新访问流」这类实时视图需要 KEYS 扫描或额外表，v1 做不了 |
| 去重靠永久表 | visitor_daily/ip_daily 无限增长，只能靠任务清理 |
| 单存储职责不清 | 明细、去重、聚合、配置全在一个库里，无法按冷热分层 |
| 不满足 R1-R5 | 用户明确要求 Redis 热存 + SQLite 归档的分层 |

## 4. 可保留资产

| 资产 | 复用方式 |
|---|---|
| `lib/db.ts` 建表/时区函数 | 保留，删去重两表 |
| `lib/track.ts` UA/Referer/IP 解析脱敏 | 原样复用（feed 的设备标签也用它） |
| `lib/auth.ts`、登录/站点 UI、`public/m.js` | 不动 |
| `app/api/health`、`scripts/health-monitor.mjs` | 扩展 Redis ping |
| events/daily_stats/page_daily/referrer_daily 表结构 | 归档侧沿用 |
| seed 演示数据生成逻辑 | 改为双路径写入 |

## 5. 结论

v1 的聚合表设计在归档侧全部保留价值（趋势查询仍走 SQLite 日聚合）；需要重造的是**写路径**（Redis pipeline）与**读路径**（混合查询），并新增归档任务。
